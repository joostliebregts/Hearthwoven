# KritterStats integrity rules: nothing counted twice, nothing missed

Joost's ask (2026-10-07): every number must be honest. Each rule below names its test: `test/Program.cs` (unit, real
game types) and `selftest/SelfTest.cs` (runtime on the Docker test server with all production mods).

Principle: **we only read.** KritterStats never changes, blocks or replaces what another mod does. Where another mod
changes how things work (MultiUserChest, craft-from-chest mods), we read the messages it already sends and fall back
to the plain rule when it is absent.

## Chests, carts, ships, tombstones (server, no player mod needed)

| # | Rule | Why | Test |
|---|---|---|---|
| C1 | **What** changed = the server's own previous copy vs the new copy of the item list, read in `ZDO.Deserialize` (prefix keeps the old copy, postfix compares). | 0.1.0 remembered the first sighting after every server start and so **missed the first change to every chest after each restart**. The server's copy comes from the world save, so nothing is missed. | unit C1, runtime C1 |
| C2 | An update that arrives twice changes nothing and counts nothing. Unchanged bytes are skipped without parsing. | Revisions and resends must never double-count. | unit C2, runtime C2 |
| C3 | Items are counted per prefab + maker + quality; stacking, splitting and moving inside a chest are no events. | Sorting a chest is not a contribution. | unit C3 |
| C4 | Quality is part of the item: swapping a quality 1 for a quality 3 sword is a take and a put. | 0.1.0 saw no change. | unit C4 |
| C5 | A container nobody built (dungeon, camp, world chest) that gets its first item list = `loot-spawned`, never a `put`. | The game generates loot when the first player opens it; that is not a gift from the opener. | unit C5, runtime C5 |
| C6 | A tombstone is `grave-drop` / `grave-take`, never a chest gift. | Dying is not stocking a chest. | unit C6, runtime C6 |
| C7 | A player-built container seen for the first time (new, or never opened before) counts as `put`. | Its empty start is real. | unit C7 |
| C8 | **Who**, two players in one chest (MultiUserChest): the add/remove/consume/drop requests that pass the server name the mover, item and amount; they are matched against the diff. The manager's **answers** pass the server too: a failed request is removed, a partial one gets the real amount, and a drop onto an occupied slot books the item that came out as the friend's take (swap). Unanswered requests expire after 15 s. A maker name without a crafter id is ignored, as the game does. | MUC lets several players use one chest; its manager's PC sends the combined change. | unit C8, C8b, C8c, swap, failed add/remove, maker; runtime C8 |
| C9 | **Who**, otherwise: the PC that sent the change (`RPC_ZDOData` sender). Plain Valheim allows one player per chest, so that is exact. If the sender is not the chest's manager (craft-from-chest mods), the line says `sender-not-owner`; if nobody had the chest open (the game's `InUse` flag) it says `unattended`. A chest a mod empties by itself (SmelterUpgrades' Stoker's chest, `*feeder*`) logs those takes as `auto-feed`, never as a player's take. | AzuCraftyBoxes pulls from chests it does not own; the Stoker's chest runs on whoever owns that area (verification F1, 4 in the world). | unit C9 (x2) |
| C10 | Smelter/kiln outputs drop on the ground and are not chest events. The cargo of a sunk ship or broken cart goes into a `CargoCrate`: that is `salvage-drop` / `salvage-take`, never stocking. | Verification F4 (2 crates in the world). | unit C10 |
| C11 | An item list in an old format (before item version 108, still loadable by the game) is read as unknown: its first change counts nothing instead of the whole chest. | Verification F6 (latent: the world is all 109 today). | unit C11 |
| C12 | The log carries markers: `world-saved` and `server-start`. Changes after the last save that a restart without saving rolled back are dropped by the companion; changes after the newest save are marked provisional. A removed object revived by a late update is ignored. | A stop does not save (AGENTS.md); verification F5, F7. | `test_kstats.py` C12 |

Every line in `chests-<date>.jsonl` carries `via` (`sender`, `shared-chest`, `sender-not-owner`) so a reader can see how
sure the attribution is. A server with a different shared-chest mod than MUC falls back to C9.

## Player data (client sends, server stores)

| # | Rule | Why | Test |
|---|---|---|---|
| P1 | The character's own counters (`profile`): absolute snapshots of stat slot 0 only, latest wins. | Other slots overlap and double-count (DudeWhatAreMyStats lesson). | unit "only slot 0" |
| P2 | Measured values are absolute **per session**; the server keeps the latest copy of every session in `players/<id>/sessions/<session>.json`. **Measured total = sum over sessions of each session's latest copy.** | 0.1.0 kept only `players/<id>.json`, so a new session overwrote the measured values of the previous one. | unit P2 |
| P3 | A session = one connection: tallies reset and a new session id starts when a connection starts (`ZNet.Awake`), not in `Logout` (which can be cancelled and is not called when the link drops). | Verification F13. | code review (`Plugin.NewConnection`) |
| P4 | The event log stores damage in one-minute UTC buckets (those older than 3 h 10 min fold into ten-minute ones, so the log and what is shared stay small) per biome, enemy, cause and type, plus each death (time, biome, killer, cause, up to the last 30 s of damage; deaths from before 0.6 keep 10 s). Burning and poison ticks are credited to whoever set you on fire or poisoned you in the last 30 s. | Joost's per-biome page with time filter; "which potion next time". | unit P4 |
| P5 | Limits: a crash or lost link loses at most the last interval (5 min default) of measured data; the log caps at 4000 buckets (overflow to an `other` bucket) and 200 listed deaths (`deathsNotListed` counts the rest); a snapshot over 200 parts is rejected with a warning in the server log. Nothing is dropped silently. | Verification F9. | unit P5 |
| P6 | Kills: `enemyKills` table 0 is the total; the other tables repeat the same kills per modifier. Only table 0 may be summed. Feast bites count as feasts only (not also as food made by "unknown"). Parries follow the game's own rule. | Verification F8, F11, F12. | companion reads table 0; code review |
| P7 | **Since install on your own PC**: the panel shows previous sessions + this one. `BepInEx/Hearthwoven/local/<playerId>-<name>.json` (one file per character: id + name, since a copied `.fch` keeps the id; 0.6.1) keeps the earlier sessions folded into one number per kind (`previous`) plus the latest saved session under its id (`lastSession`); saving that session again **replaces** it, a new session id first folds the old one in. Saved on every send interval, on logout and when the game closes (atomically: temp file flushed to disk, then replace, the previous save kept as `.bak`; a missing or unreadable file falls back to the `.bak`, logged once); loaded on spawn. A file from before 0.6.1 (`local/<playerId>.json`) moves to the character that loads it only when exactly one character on this PC with that id fits it (its baselines at most that character's game counters); otherwise it is left as it is and never merged. Unknown top-level keys are written back unchanged, so an older version keeps a newer one's data; `version` is the breaking-format number, additive changes bump `schema` only. Per **character**, across all worlds and servers (the scope of the character's own counters beside it). Only folded counters, never raw events: the per-hit event log (Battle's time windows) stays per session. Folded next to it, bounded by the biome list (600 keys at most): damage dealt and taken per biome and damage type, and deaths per biome (`biome` under `previous` and `lastSession`; Battle's All overview keeps its biome strip from it); a file from before it says per biome counts from the day it was first loaded (`biomeFrom`). Not folded: which fall, which killer, which weapon per biome (Battle's All lists this session's falls and has Damage dealt without a biome). A crash loses at most the last interval; no file (older install, new character) starts at zero; an unreadable file is set aside, a newer format left alone. NaN/Infinity are never written (0) and read as 0. | The panel said "since install" but every measured number reset each session (Joost 2026-10-08). | unit P7 (x13), panel "Defense since install" |

Estimates are never mixed in: retroactive numbers (world save, backups) stay in the companion and are labelled
`estimate`; see README design rules.

## The server's book (0.6, server, no player mod needed for the counting)

| # | Rule | Why | Test |
|---|---|---|---|
| B1 | **Cargo sent and delivered**: ships and carts only (chests are storage). Per ship or cart a first-in-first-out list of lots: a put adds (item, count, x/z, who), a take uses up the oldest lots of that item and books count x the straight line between the lot's put point and the take point. The leg is credited as "sent" to the loader and "delivered" to the unloader, never summed. A side with `via` `unattended`, or a player without an id, credits nobody; a take with no lot behind it books nothing. Read from the chest log's events as ChestWatch writes them (C1-C12 apply). | FEASIBILITY-06 option A, Joost's "who loaded and who unloaded". | unit SB cargo (x12), SB real log (8 Oct haul: 1 951.7 item-km iron sent and delivered, as FEASIBILITY-06 measured); runtime "0.6 cargo" |
| B2 | **Born near**: a ZDO new to the server (its prefab is still 0 when its first data arrives, ZDOMan.RPC_ZDOData -> CreateNewZDO) that is a young animal (prefab with Growup and Character) and tamed is one birth, credited once to every player within 40 m (3D, the peer's reference position). Once per object (remembered ids, bounded), never a removed object revived. Wild young (not tamed), adults and later updates of the same animal are no births. One line per birth in `births-<date>.jsonl`. Worded "born near", never "bred by": the game does not record who fed them. | FEASIBILITY-06 section 2 (server watcher): complete for the group, whoever's PC hosts the animals. | unit SB born (x2); runtime "0.6 born near" (x2) |
| B3 | **Restart-safe**: the book is written with every world save (temp file flushed to disk, then replace; the save before stays as `.bak`) and loaded at start, so a restart without a save rolls it back with the world (C12). An unreadable file falls back to the `.bak`. A dedicated server without a book rebuilds the cargo once from **this world's** chest logs, with C12 (events after the last save are dropped): markers name the world (0.6.1), lines under unnamed markers belong to the first world a marker names. An unreadable or newer file is set aside, never overwritten. | A stop does not save (AGENTS.md rule 3); a new world must not inherit the old one's cargo (RESILIENCE-06 I8). | unit SB restart (x3), SB rebuild; AT (x4), WO (x4) |
| B4 | **Bounded**: 128 ships and carts (the one untouched longest goes first), 200 lots each, 150 items or creatures per player and table, 500 players; only the 24 largest of each table travel to clients. | Uptime of months. | unit SB bounded (x4), SB shared |
| S5 | **Group answer**: each share file is packed once per version (write time and length); a requester gets only the copies changed since it was last served, every copy again every 5 minutes and after it switched sharing off; the names go out with every answer. After the names the list carries the book (tag `hw-book-1`, gzipped JSON: your part and each sharer's); a client before 0.6 reads the names and stops, a server before 0.6 sends names only. | OPTIMISE-06 item 1. | unit GS (x9), WIRE (x6) |

| R1 | **Server files are written whole**: `players/<id>.json`, `sessions/<session>.json`, `<id>.share.json` and the book go through AtomicFile (temp, flushed, replaced, one `.bak`); a crash or full disk never leaves a truncated file. Unsharing removes the `.bak` too. | RESILIENCE-06 B3/D1 (Joost: atomic writes + one backup). | AT (x5) |
| R2 | **What a snapshot must pass**: parts of at most 3 000 bytes, at most 200 parts; a message still incomplete 2 min after its first part is dropped, at most 4 incomplete per sender; at most one snapshot per sender per 20 s (a logout, quit or share change may come sooner, once per 20 s, not within 2 s); at most 600 000 bytes packed and 4 MB unpacked, read in blocks (a gzip bomb never inflates); exactly one JSON object (strict reader, depth 64; NaN/Infinity pass). Each problem is logged once per sender, never per message. | RESILIENCE-06 A1, A9, A11, B8. | IN (x16) |
| R3 | **Old daily logs are compressed, never deleted** (Joost): `Server.CompressLogsAfterDays` (default 30, minimum 2, 0 = off), once a day on a worker thread: `<name>.jsonl` becomes `<name>.jsonl.gz`, removed only after the .gz reads back byte for byte. The book rebuild and kstats read `.jsonl.gz` too. Routed damage is logged only with `Server.LogRoutedDamage` on (off by default, Joost 2026-10-09). | RESILIENCE-06 B2. | LG (x8), `test_kstats.py` B2; runtime "routed damage" (x2) |

## Non-enforced install (nobody gets kicked)

| # | Rule | Evidence |

## Seeing each other (reciprocal sharing, Joost 2026-10-07)

| # | Rule | Test |
|---|---|---|
| S1 | One choice, `Client.ShareWithGroup`, ON by default: "Do you want to see other players' stats? Then you'll share yours as well." The snapshot carries `share`. | unit S1 |
| S2 | Others see the same snapshot without death positions (biome stays) and without the list of worlds you played. Web pages strip positions too. | unit S2 (x2) |
| S3 | The server keeps `players/<id>.share.json` only while that player shares and serves the group only to a requester whose own share file exists. Switching off is its own message (`ShareState`, on every spawn and on change), so it works with SendStats off; copies not refreshed for 14 days are no longer served (covers uninstalling). Each answer starts with the current list of sharers, so a player who stopped sharing disappears from everyone's panel. One answer per player at a time, at most every 20 s, a queue cap of 600 parts, one part per 100 ms. The reader is linear and refuses nesting deeper than 64. | Verification G1-G5. | unit G3, G4; runtime pending |
| S4 | The web page of a player who does not share shows only their own data, with a line on how to turn sharing on. | `test_kstats.py`, screenshot |
| S6 | Fellows are keyed by who they are, not by name: the server puts the sender's platform id (`Steam_…`/`Xbox_…`, as the game gives it) in front of each shared copy and lists each sharer's key after the book; the client keys by platform id + profile id, else profile id (an older server), else the name (marked `name:`). Two players with one name both show ("Rowan (2)"); an older client reads the names and stops before the keys. A host (a world hosted from the game) keeps its own copy and builds its group locally, as a dedicated server does; singleplayer shows one line. | `FellowTests` (ID, SAME, MIX, WIRE, BOOK, SERVE, HOST), `FellowPanelTests` |
